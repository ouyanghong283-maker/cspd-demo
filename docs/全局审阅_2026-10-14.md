### S1 · P1：项目桥接丢失锁定报价的付款条件

- 位置：`src/app/core/store.ts:1486`，对照同文件 `loadProjectContract()` 的付款字段处理。
- 触发：锁定付款条件为“100%预付”的报价，赢单，再由销售创建交付项目。
- 影响：合同金额和报价版本来自锁定报价，付款条件却变成固定“签约30% / 发货60% / 验收10%（样例）”。不同项目创建入口得到不同合同条款。
- 证据：通过现有测试 harness，准备 DEMO-O014 草稿后，调用保存报价、财务确认、提交审核、主管通过、记录发出、客户接受、申请锁定、主管锁定、赢单和 `bridge()`。输出 `quotePayment="100%预付"`，`contractPayment="签约30% / 发货60% / 验收10%（样例）"`，两者引用同一报价版本。
- 建议：统一合同生成逻辑，付款条件引用锁定报价；没有锁定报价的旧流程才使用明确标注的样例默认值。重复逻辑已经产生数据分叉，是 Duplicated Code 的判断性发现。

### S2 · P1：交底关键内容修改后，旧审核继续有效

- 位置：`src/app/core/forms.ts:497`、`src/app/core/store.ts:1527`，启动任务校验见 `store.ts:1816`。
- 触发：PM 对审核已通过的项目修改验收标准、订单生产周期或调试交期。
- 影响：表单保留旧 `briefing.review`，整项目保存不标记重新复核；新条件继续沿用原审核结果，后续任务校验仍认为审核有效。
- 证据：对 DEMO-P003 调用 `saveProject()` 修改验收标准后，得到 `review="通过"`、`needsReview=false`，验收标准已是新的内容。表单实际保存路径调用同一方法。
- 建议：识别交底关键字段变化，保留原审核历史，标注新内容待复核，并让启动完成门槛检查当前内容的审核状态。

### S3 · P2：演示文档的财务确认顺序会卡住最终锁定

- 位置：`README.md:25`、`src/app/core/store.ts:706`、`src/app/core/store.ts:892`。
- 触发：按 README 的快速演示顺序，记录发出、客户接受后才进行财务确认。
- 影响：财务确认只允许草稿或退回补充；最终锁定要求财务已确认。之前未确认的已发报价无法按这条路线继续锁定，需要新版本重走流程。
- 证据：对已发报价执行财务确认，返回“仅可在报价草稿或退回补充状态调整财务口径”；锁定条件也确实检查财务确认。
- 建议：将指引统一为提交审核／发出前完成财务确认。保持已发报价历史内容的稳定性。

## 需求实现（Spec）

### R1 · P1：旧线索迁移错误地清空有效分配状态

- 位置：`src/app/core/v4.ts:78`。
- 需求：`doc/PRD/DEMO PRD/V4PRD/子项目需求/01_CRM线索状态与迁移.md:86` 规定“待跟进且负责人明确对应”迁移为 CRM 已分配；第 88 行规定暂缓／归档也按有效负责人判断分配信息。
- 触发：旧线索没有新 `crmStatus`，但原负责人已明确对应有效演示账号。
- 影响：迁移一律填“未分配”，销售失去编辑与转换资格，必须主管重新分配。
- 证据：保留 DEMO-L001 的负责人“张销售”和有效 `ownerPersonId`，移除新增状态字段模拟旧数据；执行 `migrateV4()` 后状态为“未分配”。
- 建议：按有效身份对应关系和转换关联推导迁移状态，保留来源与原历史。

### R2 · P1：SAT／客户验收变更后，当前结果与计划完成状态矛盾

- 位置：`src/app/core/store.ts:1974`、`src/app/core/store.ts:1995`；完成任务写入见 `completeAcceptance()` 和 `receive()`。
- 需求：`doc/PRD/DEMO PRD/CSPD平台_业务上手演示版_DEMO_PRD_V1.1_2026-10-10.md:329` 要求已完成关键节点改结果后标需复核，SAT 不再满足移交前置，并保留历史。
- 触发和证据一：通过真实 `receive()` 接收 DEMO-P007 后，内部移交 WBS 为已完成；再通过 `saveSat()` 改成不合格草稿，SAT 未完成，但移交仍为已接收、内部移交 WBS 仍为已完成。SAT 路径确实会设置项目需复核，缺口是完成状态之间的表达与同步。
- 触发和证据二：逐项通过客户验收并调用 `completeAcceptance()`，WBS 为已完成；再将任一项改为不通过，`acceptanceComplete=false`，WBS 仍为已完成，且该保存入口不设置需复核。
- 影响：用户看到的检查项、任务进度和完成结果不一致；验收修改缺少明确复核状态。
- 建议：保留过去接收与签认历史，给当前结果和对应 WBS 建立明确复核状态；重新确认后再解除，避免一个布尔值清除其他待复核事项。
- 补充：初始 DEMO-P008 已接收样例本身也存在 SAT 已完成而对应 WBS 未开始的矛盾，需要在修复后同步整理样例。

### R3 · P1：丢单后报价审核／锁定待办仍未解除

- 位置：`src/app/core/store.ts:1333`。
- 需求：`doc/PRD/DEMO PRD/补丁V2PRD.MD:232` 明确“待审核及锁定申请待办随关闭解除，报价历史保留”。
- 触发：提交报价审核后将商机关闭为丢单；锁定申请同理。
- 影响：代码只解除冷却提醒，主管仍会看到已丢单商机的报价审核／锁定待办。
- 证据：准备 DEMO-O014，调用 `submitQuote()` 生成真实待办，再调用 `closeSale(...,'丢单',...)`；商机为丢单，`quote-review-DEMO-QV-002-1` 的 `resolved=false`。
- 建议：按商机关闭事件解除当前报价审核与锁定申请待办，保留报价及操作历史。

### R4 · P1：赢单写入口可跳过业务阶段

- 位置：`src/app/core/store.ts:1320`。
- 需求：`doc/PRD/DEMO PRD/补丁V2PRD.MD:231` 的动作是“合同谈判→赢单”；原业务上手需求第 326 行要求不跳过阶段；子项目 `02_CRM人员权限与关联查看.md:36` 要求按钮与写操作都检查对象规则。
- 触发：在意向沟通等早期阶段直接调用 `closeSale(...,'赢单',原因,成交日期,'')`。
- 影响：沟通门槛仅在当前已经是合同谈判时检查，早期阶段可直接赢单。当前普通 UI 通常不提供这个按钮，因此这是写入口缺口，不能宣称已复现普通用户点击绕过。
- 证据：DEMO-O001 在意向沟通且没有报价系列时，调用该写方法返回 `true`，阶段直接变为赢单。
- 建议：赢单入口限定当前阶段为合同谈判，并检查当前报价流程应满足的最终锁定和沟通条件；丢单仍允许任一未关闭阶段。

## 处理建议

优先修复锁定付款条件丢失、已审核资料变化后的复核机制、旧线索迁移和丢单待办；再完善赢单写入口与演示指引、更新过期测试。完成后需在允许启动 4201 服务的环境重跑同一对象连续主线及结果变更分支，再检查刷新、重置和各角色交接。

Standards 共 3 项，最高影响是锁定付款条件在项目桥接中丢失；Spec 共 4 项，最高影响包括旧线索失去分配资格与关键节点结果／完成状态矛盾。另有 1 项测试版本断言维护问题。

# 联系人关联链修复与验收

## 原因与复现

真实表单回调复现：线索草稿没有联系人 ID，在客户页补齐首位联系人并保存后，客户记录更新，但线索的 `contactId` 仍为空。转换通过该 ID 找联系人，因此已填写信息仍被报告缺失。

修复前运行 `node --import tsx tests/contact-chain.test.ts`，断言“已填写联系人却没有关联到线索”失败，实际 ID 为空；修复后相同回调、保存和转换路径通过。

## 修复范围

- 保存客户的唯一联系人时，为当前角色可操作、未转换、尚未指定联系人的线索补齐关联。旧草稿已经存在唯一联系人时，转换在同一事务中保存确定的联系人 ID，并传给商机。多联系人或无效旧 ID 要求明确选择。
- 客户和联系人下拉选项以稳定 ID 为值，同名记录通过国家、联系方式和编号区分；客户切换后清空旧联系人并更新选项。必填和选填区均使用同一联动规则。
- 新建线索一次性保存客户、联系人和线索。客户对象在保存前克隆，失败不发布任何部分变更，保存后调用方修改也不能改动已发布状态。
- 商机已有报价系列时，禁止直接更换客户；报价保存、审核/发出门禁及最终锁定检查客户和联系人归属，防止旧客户报价进入新客户流程。

本次处理第二轮全局审阅中直接相关的 S2-1（商机/报价客户错配）、S2-4（失败后部分客户变更）、R2-2（姓名代替稳定 ID）及客户对象别名问题。其他计划、财务权限、关键凭据问题不在本次联系人关联修复的结论范围内。

## 验证

新增六项回归见 [contact-chain.test.ts](../tests/contact-chain.test.ts)，覆盖真实客户表单补录后转换、旧草稿恢复、同名客户/联系人、联系人跨客户错配、联合保存失败和报价错配。

既有完整主线加入客户/联系人 ID 断言：线索→商机→报价锁定→赢单→合同→项目→交底→SAT→客户验收→移交。链路中客户和联系人 ID 必须保持一致。

测试和生产构建结果见 [测试日志](../artifacts/contact-chain-2026-10-14/npm-test.log) 和 [构建日志](../artifacts/contact-chain-2026-10-14/build.log)。本轮使用内存状态及真实表单保存回调验证，没有读取或重置用户的浏览器业务数据。

最终结果：7 个测试文件全部通过，新增联系人链路 6 项回归通过，完整销售至移交主线通过，生产构建通过。浏览器复核脚本也已改为选择联系人 ID，并检查客户补录后的线索关联；脚本语法检查通过，实际浏览器执行仍待可监听环境。
